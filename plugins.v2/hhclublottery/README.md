# HHCLUB 幸运大转盘

把 [HH-Automatic-lottery](https://github.com/SAGIRIxr/HH-Automatic-lottery) 的命令行版移植为 [MoviePilot](https://github.com/jxxghp/MoviePilot) 插件。原来写在脚本 / 配置文件里的那些项全部改成配置页上的**勾选和填写**，不用青龙、不用 crontab；**Cookie 除了手填，还能直接吃 MoviePilot 设定里已经配好的 CookieCloud**。

抽奖逻辑与上游共用一套口径：按转盘时长自适应延迟、限流补枪与阶梯退避、VIP 折算按等级判定、抽奖站内信清理、v4 统计结构。

## 目录结构

```
hhclublottery/
├── __init__.py       # 插件主体（HHClubLottery 类）：调度、Cookie、备份、数据页
├── config_form.py    # 配置页的 Vuetify JSON（260 多行纯拼装，不碰 self）
├── lottery.py        # 抽奖核心：站点交互 + 统计口径，不依赖 MoviePilot
└── README.md
```

没有 `requirements.txt` —— 只用到 `requests`，MoviePilot 自带。

## 安装

MoviePilot → 设定 → 插件 → 插件仓库，添加 `https://github.com/SAGIRIxr/MoviePilot-Plugins`，然后在插件市场安装 **HHCLUB幸运大转盘**。

## Cookie 三种来源

| 来源 | 说明 |
|------|------|
| **手动填写** | 浏览器登录站点 → F12 → Network → 任一请求的请求头里 `Cookie:` 整行复制粘贴进来 |
| **CookieCloud** | 直接用 MoviePilot「设定 → 站点 → CookieCloud」里已配好的服务器 / KEY / 密码，插件不再单独填一遍 |
| **MoviePilot 站点管理** | 取站点库里该域名的 Cookie（MoviePilot 自己也会用 CookieCloud 定时刷新它） |

后两种都按「站点域名」这一项去匹配，默认 `hhanclub.net`。CookieCloud 那边用域名末两级做分组 key，正常填 `hhanclub.net` 就能命中；万一填了完整 URL 或带子域名，插件会再做一轮宽松匹配。

用 CookieCloud 的前提是**浏览器端的 CookieCloud 插件同步范围包含本站，且你最近在浏览器里登录过**。取到的 Cookie 里缺 `c_secure_uid` / `c_secure_pass` 就说明那不是登录态，插件会在日志里先提醒一句再往下走。找不到该域名时，日志会把 CookieCloud 里实际有哪些域名列出来一部分，一眼就能看出是不是同步范围没覆盖到。

> **Cookie 等于你的账号。** 站点每人只能有一个号，所以这里没做多账号。

## 配置项

**基础** —— 启用插件 / 开启通知 / 立即运行一次 / 停止当前抽奖 / 抽奖周期

**抽奖周期可以留空**。抽奖花的是真憨豆，默认不该自己跑起来 —— 留空就只在你点「开始抽奖」时跑；填了 cron 才会定时触发，两条路并存。

**手动开始 / 停止在数据页上**：顶部状态卡带 ▶ 开始抽奖、■ 停止、🔄 刷新三个按钮，点一下就走插件 API，不用去配置页勾开关再保存。卡上还写着在不在跑、本轮第几抽、当前余额，按钮会按状态自动置灰（跑着的时候开不了第二轮，没跑的时候停不了）。

跑着的时候状态卡上有：**进度条 + 第 N / M 抽**（一抽到底没有终点，就不画条）、**本轮消耗 / 获得 / 盈亏 / 余额**、**已跑时长 + 预计还要多久**（按已经抽出来的速度估，限流和退避都算在里面）、**本轮大奖**、**本轮奖品小结**。

大奖（VIP、780,000 以上憨豆）单独一行摆在最前面。混在类别汇总里是看不出来的 —— 中了 780,000 只不过让「💰 憨豆 ×10」变成「×11」，而那一注顶得上三百多抽的消耗；VIP 更是被按次数排到了最后一位。VIP 那行会连折算额一起写，且不在下面的汇总里重复出现。

> **页面不会自己刷新。** MoviePilot 的 vuetify 渲染模式只在打开数据页时拉一次，之后不轮询。所以挂机时看进度要点「刷新」—— 它调的是一个什么都不做的 `/status` 接口，前端在 `events.click` 调完后会 `emit('action')`，容器收到就重新拉一遍整页。这是这个渲染模式下唯一能拿到的刷新手段。
>
> **点刷新时整页都会更新**，不只是状态卡。抽奖途中，历史总计、奖项明细、大奖名册读的是运行中那份实时统计 —— `total` 只在一轮跑完时才写库，否则挂机抽五千次的中途点刷新，下面几张卡会一直停在开跑前的数字，看着像没在记。

配置页那两个开关（「立即运行一次」「停止当前抽奖」）保留着当备用入口，行为和按钮一致。

**抽奖**

| 配置项 | 默认 | 说明 |
|--------|------|------|
| 每次抽多少次 | `10` | 填 `0` = **一抽到底**（会一直抽到余额跌破保留线）。留空不等于 0，留空按默认值 10 走 |
| 保留憨豆 | `0` | 一抽到底时留多少不动 |
| 定时结束(分钟) | 留空 | **留空 = 不限制**；填了就到点收工，最多 `4320`（3 天）。开着时状态卡、大奖通知、定时战报都会带上「还有多久」 |
| 自适应延迟 | 开 | 按上一抽返回的转盘时长排队（推荐），开启后固定间隔完全不参与 |
| 自适应缓冲(ms) | `0` | −500 ~ 5000，负值更贴边、正值更保守 |
| 固定间隔(秒) | `6.8` | 仅在关闭自适应时生效，最小 3 秒 |
| 清理抽奖站内信 | 关 | 途中每 25 抽扫一次第一页，收尾翻一遍整个收件箱；只删主题带「幸运大转盘」的 |
| 中 VIP 就收工 | 关 | 已折算成憨豆的那一注也算 |
| 中 780,000 憨豆就收工 | 关 | 只认这一个精确档位，不含 1,000,000 等其他档 |

**通知** —— 中大奖即时推送（下拉勾选，可选 ⭐ VIP / 💰 780,000 以上憨豆 / 📧 邀请；一样都不勾 = 不推）/ 定时战报 / 战报间隔

**备份导入** —— 见下面「备份导入导出」

**其他** —— 使用系统代理 / 运行记录保留天数 / 自定义 User-Agent

## 它会自己处理的几件事

- **自适应延迟** —— 站点的冷却窗口就等于上一抽返回的 `data.duration`（线上实测 3976~7666ms 随机），所以任何固定间隔都躲不掉「不要重复点击」。计时起点是**请求发出**那一刻，响应传输和记账的耗时也算在冷却里。被挡回不扣憨豆也不重置服务端计时，300ms 后自动补一枪。
- **不因为失败几次就收摊** —— 站点报错、网络不通、被限流各自单独计数，等待每 3 次抬一档（×1.5）一路到 5 分钟封顶，站点恢复就自动接上。只有「憨豆不足 / 次数用完」这类明确终止信号才立刻停。
- **VIP 折算** —— 抽奖页写着「已是 VIP 或以上等级时中 VIP 改发憨豆 1000000」，但接口返回的文案还是 VIP。中到 VIP 会回服务端核余额 + 查等级（按 NexusPHP 的 class 序号，不看被站点改过的等级名），确认折算后**这一注仍计为一次 VIP 中奖**，只把收益记成憨豆 —— 爆率统计和盈亏两头都不错。金额一律按站点公布值，不拿余额差当金额（做种收益会把它污染成「1,000,060 憨豆」这种不存在的档位）。
- **中大奖就收工** —— 两个条件各一个开关，和「大奖通知门槛」互不影响（通知想宽松、停机想严格是两回事）。停之前会回服务端拉一次权威余额 —— 开这功能本来就是为了停在中奖那一刻对账，运行记录里摆个本地估算说不过去；VIP 那一注折算核对时刚校准过就跳过。
- **单抽消耗变了** —— 每次开跑前读页面上的实际值，站点调价自动跟上。
- **请求失败会说清是怎么失败的** —— 站点掉登录时是拿 HTTP 200 回一张登录页。既然现在不因失败次数收摊、会一直重试下去，只记一句「请求失败（HTTP 200）」等于什么都没说。现在按 网络错误 / 401·403 / 非 2xx / 200 但不是 JSON 分开讲，认出登录页就直接说「去页面上重新登一下」。
- **保存配置不打断** —— MoviePilot 保存插件配置走的是同一个实例的 `init_plugin`，不经过 `stop_service`。所以改 cron、调通知开关都不会把挂了一半的抽奖腰斩；本轮继续按开跑时的设置跑完，新配置下一轮生效。要中途收手就用「停止当前抽奖」。
- **停用 / 重载插件** —— 抽奖循环当场收工，已抽的成绩照样落盘，不会丢。

## 数据页

抽奖说到底就是拿憨豆换憨豆，所以整页围绕憨豆盈亏来排：

**憨豆盈亏（历史总计）** —— 累计消耗 / 累计获得 / **净盈亏** / **回本率** / **当前余额**，每项下面带「每抽多少」。当前余额在抽奖时是运行中那份的实时读数，空闲时是上一轮收尾的读数、副行注明截至什么时候（做种收益一直在涨，不说清楚就是在骗人）。`每抽 +116.7 憨豆` 这种数比「一共抽了三万次」有用得多。获得那一栏会拆成 `档位 X + 折算 Y`，因为折算来的憨豆不在任何档位里，不点明的话拿档位乘开会对不上。

**奖品累计（憨豆以外）** —— 彩虹ID、补签卡、上传量、邀请、改名卡各按自己的单位显示累计值和中奖次数。**没中过的也占位** —— 「邀请 0 · 没中过」本身就是信息。VIP 比较特殊：被站点折算成憨豆之后天数会被扣回 0，所以主值取**次数**，折算额放在下面一行，否则看着像一次都没中过。

**奖项明细** —— 类别一行、**每个档位各一行**（不再是挤在一个格子里用顿号拼），每行都带次数、实测占比、**折合憨豆**。

「折合憨豆」只算真进账的憨豆：彩虹ID / 补签卡 / 上传量的单位是天 / 个 / GB，换算不了也不硬凑，留空；VIP 那一行是被站点折算成的憨豆。**这一列的表尾合计恒等于「累计获得」**，对不上就说明哪一类算漏了。

有了这一列才看得出哪一档真正在回血 —— 比如 780,000 憨豆那档只占 0.06% 的抽数，却贡献了全部憨豆收益的四分之一还多，这在旧版页面上完全看不出来。

**大奖名册** —— 标题写的是 `大奖名册（中过 31 次，1 条有时间记录）`。

**MP 这边中到大奖会当场记一条**（VIP，或 780,000 以上的憨豆），条目形状和油猴版一致（`{at, text}`、新的在前、封顶 100 条），所以两边的名册合并时对得上、去得了重。

标题里那两个数是分开来的：**中过几次**在 `prizes` 里一直是准的（VIP 次数 + 780,000 以上憨豆的档位次数）；**带时刻的名册**是后来才加的功能，在那之前中的只剩次数。差额会明说「其中 30 次没有时间记录」并解释来历 —— 只摆名册的话，中过 31 次却只列出 1 条，看着像丢了数据。

名册的口径**写死**，不跟着「大奖通知门槛」走 —— 那个是可配的，调到 100 图个热闹的话，名册跟着走就成流水账了。和停机开关、次数统计共用同一条口径。

一次都没中过时整张卡不显示。

**运行记录** —— 每次运行一行：抽数 / 消耗 / 获得憨豆（含折算）/ 盈亏 / **每抽盈亏** / 结束余额 / 时长 / 结束原因。

## 插件 API

| 接口 | 说明 |
|------|------|
| `GET /api/v1/plugin/HHClubLottery/export?apikey=xxx` | 导出统计备份，格式与油猴版一致 |
| `GET /api/v1/plugin/HHClubLottery/run?apikey=xxx` | 后台触发一轮抽奖，立即返回（数据页的「开始抽奖」按钮走的就是它）。插件未启用时拒绝 —— 「禁用」就该是「不会花憨豆」 |
| `GET /api/v1/plugin/HHClubLottery/stop?apikey=xxx` | 让正在跑的那一轮收工，已抽的成绩照常落盘 |
| `GET /api/v1/plugin/HHClubLottery/status?apikey=xxx` | 当前状态，无副作用（数据页「刷新」按钮点的就是它，也可供外部轮询） |

## 备份导入导出

和油猴版共用一套 v4 备份格式，两边可以互相导。

**导出** —— 数据页上点「导出备份」，浏览器直接把 JSON 存成文件（`hhclub-lottery-backup-<时间>-<抽数>draws.json`）。拿到浏览器里打开 `hhanclub.net/lucky.php`，面板上点「📥 导入备份」选**合并**，MP 上抽的和电脑上抽的就并到一块了。

**导入** —— 配置页「备份导入」卡片：把 JSON 整段粘进框里，选导入方式，勾上「执行导入」保存。导完开关自动复位、框自动清空。

| 导入方式 | 说明 |
|---|---|
| 合并 | 两边记录相加，换设备用这个（默认） |
| 覆盖 | 用这份备份取代当前历史；之后这台机器就是那条记录线的延续 |
| 强制合并 | 明知会算两遍也要合 |

**为什么要拦重复导入** —— 统计存的是累加值、没有逐抽流水，所以合并没法真去重：重叠的部分一定会被算两遍。改不了这一点，那就在动手之前认出来。三种铁证会直接拦下并说明：

- 这个文件（`exportId`）已经导入过一次
- 两份记录同源（`originId` 有交集，比如从这台 MP 导出去又导回来）
- 有大奖记录时刻完全重合（老备份没编号时的兜底 —— 同一毫秒同一个奖不会是巧合）

还有一条「时间区间整个被罩住」只算**看着像**，不是证据：两个人在同一段时间里各刷各的，抽得少的那份区间本来就会被罩住。这种只提醒一句，照常导入。

### 油猴版的大奖时间线

**带的，也能导进来。** 油猴版把名册存在 `total.jackpots`，条目是 `{at, text}`、新的在前、封顶 100 条，`backupStats()` 导出时整份 `total` 都在里面。

插件收下来时按同一套规矩收一遍：只留有文案的、字段收成 `{at, text}`、按时刻倒序、封顶 100 条 —— 手改坏的文件不该一路带到页面上。两边都有名册时合并会去重：**时刻 + 文案都一样的只留一份**，所以同一批记录导两次不会多出重影。导入台账（`imports`）同样保留，那是这边产生不了、也补不回来的东西。

### 一个改不了的限制：没有「增量同步」

统计存的是**累加值**，没有逐抽流水 —— 这是油猴版定下来的格式，两边共用。所以：

- 浏览器和 MP 两边**各刷各的、互不重叠**，合并一次是准的；
- 但你没法「把浏览器里新增的那部分同步过来」。第二次导同一条记录线的备份会被「两份记录同源」拦住，强合就是把重叠的部分算两遍。

真要以浏览器那份为准，就用**覆盖**（MP 自己抽的那些会被取代）。反过来把 MP 的战绩带回浏览器也是一样的道理。

## 清空记录

配置页「清空记录」卡片：选范围 + 勾「执行清空」保存。

| 范围 | 清掉什么 |
|---|---|
| 只清运行记录 | 每次运行那张表，统计不动（默认） |
| 只清统计 | 累计战绩、大奖名册、记录线；运行记录保留 |
| 都清 | 回到刚装好的样子 |

**清之前会自动留一份快照**，勾「撤销上次清空」保存就能原样放回来（只留最近一次）。真要搬走或长期留档，还是先到数据页点「导出备份」下一份文件更稳。

「执行清空」「撤销上次清空」「执行导入」**一次保存只能勾一个** —— 同时勾会全都不执行并提示，与其猜哪个优先，不如把话说清楚。

**抽奖途中这三个都不能做**。跑着的那一轮手里攥着自己那份统计，收尾时整份写回库；这时候动库里的数据，几秒后就会被那一份盖掉 —— 悄无声息地白干。会拦下来并提示「等跑完，或先点停止」。

抽奖途中**导出**则是可以的，导的是含这一轮在内的实时统计，和页面上看到的一致；记录线编号会同步回运行中那份，收尾落盘沿用同一个，所以那份备份日后导回来照样认得出同源。

### 导出 → 清空 → 导回来

走得通，拿 34,228 抽的真实数据验过：抽数、消耗、各类奖品累计、所有档位、VIP 折算桶、大奖名册，一字不差地回来了。

- 用**覆盖**更彻底：连记录线（`originId`）一起回来，以后再导同一个文件还认得出。
- 用**合并**也能恢复，只是会新起一条记录线，台账里记着来源。
- **只清了运行记录、统计还留着**的话，导回自己的备份会被「两份记录同源」拦住 —— 那是对的，不然就是把自己算两遍。

备份里带两个编号：`originId` 认记录线（同一台 MP 导出多少次都是同一个），`exportId` 认这一个文件（每导一次换一个）。油猴版靠它们认出「同一份文件导了两遍」并在导入前弹警告 —— 统计存的是累加值、没有逐抽流水，重复导入没法事后去重。反过来把油猴版的备份导进 MP 也行，那边的大奖名册和导入台账会原样保留，不会被下次覆写抹掉。

远程命令 `/hh_lottery` 也能触发一轮。

## 测试

抽奖接口花的是真憨豆，没法拿线上验证，所以本地起了个假站点把核心逻辑真跑一遍：

```bash
pytest tests/v2/hhclublottery -m v2
```
